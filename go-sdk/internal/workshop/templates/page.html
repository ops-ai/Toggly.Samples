What is a feature flag?

A feature flag is a named decision that lets you release code independently from enabling a feature. The application asks whether new-dashboard is on, then selects a branch. Rules can use a person, a browser, or an Order.

Your first flag, in three steps

  1. Run offline practice or create new-dashboard in your Go SDK Sample app using the README recipe.
  2. Open Gates. Switch the flag off and on. Offline practice offers local controls on that page.
  3. After the next background refresh, reload the page. Compare the feature and negated branches. Your code stayed the same.

Build the context once per request

  1. The sample selects alice/admin or bob/user from a bounded demo cookie.
  2. togglyhttp.MiddlewareWith stores a fresh context via GetContext: contextForRequest. Missing UA, language, and country fields are then filled from headers (FromHttpRequest mapping).
  3. Handlers read togglyctx.From(r.Context()) and pass that context explicitly to IsEnabled. Empty per-call fields merge from this ambient context.
  4. Template data carries the same context via TogglyContext().

There is no init-then-set-context network round trip. The shared client downloads definitions; local evaluation uses the full request context. Cookie changes affect only subsequent requests in this browser. Another browser can keep a different persona.

In your app, build identity/groups/claims from a verified principal. Populate request metadata from headers you trust. Our Matching/Non-matching values are synthetic inputs for repeatable learning.

Signed definitions and lifecycle

All configured clients request signed definitions with signature verification enabled. Offline practice uses an ephemeral ES256 key on loopback; tests also tamper with signatures and verify that the last accepted state is retained. No private key is stored. The published variant endpoint path does not reject an envelope that omits its signature or key ID; this limitation is documented in the README. Normal signed responses and tampered signatures are exercised here.

The SDK refreshes in the background. Reload any page or read the current JSON snapshot to see new evaluations. A page is a snapshot at request time; it does not update itself. NewClient is asynchronous, so the initial response may show loading and OFF defaults.

The process calls Close once for each of its three clients after HTTP shutdown. Request cancellation is checked by sample handlers and passed to programmatic evaluation. Native template helpers internally use context.Background and suppress evaluation errors; they are suitable for presentation, while actions use the HTTP gate.

Other supported surfaces

A native in-memory SessionStore is configured. Percentage is already deterministic for stable identities. The SDK also supports snapshot providers, custom filters, usage batching, and metrics. This sample disables outbound telemetry and avoids persisting app definitions; see the README for API pointers.
